Develop with Claude Code inside a sandbox you can always return to

Your project stays on your computer. Claude Code runs confined to that project: in a rootless Podman container on Linux, or in macOS's own Seatbelt sandbox on a Mac, with Xcode and Swift running natively. Conversations and logins are kept outside the sandbox, so tomorrow you continue exactly where you stopped.

    One-time setup
    
      
    Do these once per computer, in order. Tick each step as you finish; your progress is remembered in this browser.
    
      
      

        
    1. 
          
      Install Podman
      
          
      You need Podman 4.3 or newer, run as your normal user. Never put sudo in front of podman for this setup: that would make the containers rootful.
      
          
      
            
      
              
              
              
              
            
      
            
      
              
      sudo dnf install -y podman git
      
              
      Fedora 38+ and RHEL 9 are ready for rootless use out of the box, including SELinux labelling.
      
            
      
            
      
              
      sudo apt update
sudo apt install -y podman uidmap passt netavark aardvark-dns \
  fuse-overlayfs dbus-user-session git
      
              
      Use Ubuntu 24.04+ or Debian 12+. Ubuntu 22.04 ships Podman 3.4, which is too old. netavark and aardvark-dns are what let the allowlist network mode find its proxy by name.
      
            
      
            
      
              
      Install WSL 2 with Ubuntu 24.04, open the Ubuntu terminal, and follow the Ubuntu / Debian tab from there. Keep projects inside the Linux file system (for example ~/code), not under /mnt/c, for speed and correct file ownership.
      
              
      wsl --install -d Ubuntu-24.04
      
            
      
            
      
              
      The launcher and tests are written for a Linux host and are verified on Linux only. On a Mac, run them inside a Linux virtual machine such as Lima or UTM with Ubuntu 24.04, then follow the Ubuntu / Debian tab inside it.
      
              
      brew install lima
limactl start --name=dev template://ubuntu-lts
limactl shell dev

      Give your user subordinate ID ranges
      
          
      Rootless containers borrow a private range of user and group IDs that belong to you. Check you have one; most installers add it automatically.
      
          
      grep "^$USER:" /etc/subuid /etc/subgid
      
          
      If either file prints nothing, add a range and let Podman pick it up:
      
          
      sudo usermod --add-subuids 100000-165535 --add-subgids 100000-165535 "$USER"
podman system migrate

printf '[Service]\nDelegate=cpu cpuset io memory pids\n' | \
  sudo tee /etc/systemd/system/user@.service.d/delegate.conf
sudo systemctl daemon-reload

    6. 
          
      Sign in once
      
          
      Pick one. Don't set up both a subscription and an API key: the key wins and you'd be billed per token.
      
          
      
            
      
              
              
              
            
      
            
      
              
      For Pro, Max, Team or Enterprise. Start the sandbox from any project, choose the Claude account login, open the link it prints, sign in, and paste the code back at Paste code here if prompted.
      
              
      cd ~/code/my-app && claude-sandbox
      
              
      The login is stored in the claude-config volume, so every later run and every project is already signed in.
      
            
      
            
      
              
      A one-year subscription token, good for scripts and headless machines. It only makes model requests: claude.ai connectors and Remote Control need the normal login.
      
              
      claude-sandbox setup-token                       # prints the token after browser approval
printf '%s' 'sk-ant-oat01-…' | podman secret create claude_oauth_token -
claude-sandbox --auth token
      
            
      
            
      
              
      Pay-as-you-go with a key from the Claude Console. Approve the key the first time Claude asks; the choice is remembered.
      
              
      printf '%s' 'sk-ant-api03-…' | podman secret create anthropic_api_key -
claude-sandbox --auth apikey
      
            
      
          
      
          
      Secrets are mounted as files readable only by the sandbox user and loaded when Claude starts; they never show up in podman inspect. Inside Claude, /status shows which sign-in is active.

    Daily work
    
      
    
      
    Always start the sandbox from the project folder. The launcher mounts that folder at the same path inside the container, which is what keeps each project's conversations separate.
    
      
    cd ~/code/my-app
claude-sandbox -n auth-refactor     # new, named session
claude-sandbox --yolo               # no permission prompts; contained to this project
claude-sandbox --shell              # bash in the same environment: run tests, git, installs
claude-sandbox -p 3000              # dev server at http://127.0.0.1:3000 (bind 0.0.0.0 inside)
claude-sandbox -- -p "fix the failing tests"   # after --, arguments go to claude
    
      
    Files Claude creates or edits are owned by you, appear on your computer immediately, and your editor, git client and file manager work on them as usual. Run several projects at once in separate terminals; each gets its own container.
    
      
    -p means "publish port" to the launcher. To pass Claude's own print flag, put it after --, as in the last line above.
    
      
    What can and can't reach your computer
    
      
    
        
    Inside the sandboxNot available inside
    
        
    Your project folder, read-write (or read-only with --ro)
    The three volumes below
    Your ~/.gitconfig, read-only, if you pass --gitconfig    		
            The rest of your home folder, ~/.ssh, cloud credentials, other projects
    Root access, sudo, Linux capabilities
    Anything on the network that the chosen mode blocks
    
      
    
      
    Push to GitHub from the sandbox over HTTPS with a token scoped to the repository, or push from your normal terminal; the files are the same.
    
          
    
      
    
      
    Start the sandbox from the project folder. Your project isn't copied or mounted: Claude edits it in place, and Xcode, your editor and git see every change immediately.
    
      
    cd ~/code/MyMacApp
claude-mac-sandbox -n settings-window   # new, named session
claude-mac-sandbox --yolo               # no permission prompts; still confined
claude-mac-sandbox --shell              # bash with the same limits: build, test, git
claude-mac-sandbox -p "fix the failing tests"   # any other argument goes to claude
    
      
    Build and test inside the sandbox
    
      
    Claude runs these itself when you ask it to build or test; you can run them in --shell too.
    
      
    swift build && swift test
xcodebuild -scheme MyMacApp -destination 'platform=macOS' test
xcodebuild -list                        # see the scheme names
    
      
    SwiftPM and Xcode normally evaluate Package.swift in a sandbox of their own, and macOS doesn't allow a sandbox inside a sandbox. The launcher puts small swift and xcodebuild wrappers first on the PATH that switch off only that inner sandbox; everything still runs inside the outer one. Call swift and xcodebuild directly, not through xcrun, so the wrappers apply.
    
      
    Keep building and running the app from Xcode as usual: Xcode itself runs outside the sandbox. A dev server Claude starts inside is reachable from your browser with full or allowlist networking.
    
      
    Verified in CI on macOS 14 and 15: swift build, swift test and xcodebuild test of a sample project with a SwiftUI view, and fetching SwiftPM dependencies through the allowlist. iOS simulators and code signing with your developer certificates aren't covered by the tests yet; signing needs the Keychain, so don't block it for those.
    
      
    What the sandbox allows
    
      
    
        
    Allowed insideBlocked inside
    
        
    Read and write the project folder (or read-only with --ro)
    Write ~/.claude, ~/.claude.json, ~/Library/Developer (DerivedData, simulators), ~/Library/Caches, SwiftPM state and temp folders
    Read the rest of the disk, your git config, Xcode and SDKs
    The Keychain, unless you block it    		
            Writing anywhere else: ~/.zshrc, LaunchAgents, /usr/local, other projects, the Claude Code binary
    Changing .git/config or .git/hooks (they run code later, outside the sandbox)
    Reading ~/.ssh, ~/.aws, ~/.gnupg, ~/.config/gh, ~/.kube, ~/.docker, ~/.netrc, ~/.npmrc
    Your ssh-agent, and tokens in your shell environment
    
      
    
      
    Need more? --allow-write ~/some/dir adds a writable folder, --hide ~/private blocks reading one, and --allow-git-config allows git init, git config and hook changes for that run. Run claude-mac-sandbox --print-profile to see the exact rules.
    
      
    Seatbelt (sandbox-exec) is marked deprecated by Apple but is what Claude Code's own sandbox, SwiftPM and Xcode use today. The test suite runs on every push and weekly to catch changes in new macOS versions.
    
      
    Lighter option: Claude Code's built-in sandbox
    
      
    Claude Code has its own Seatbelt sandbox: run /sandbox inside Claude, or add this to ~/.claude/settings.json. It confines the commands Claude runs, while Claude's own file reads and edits follow its permission rules instead. Use it or claude-mac-sandbox, not both: the built-in one can't start inside the launcher.
    
      
    {
  "sandbox": {
    "enabled": true,
    "autoAllowBashIfSandboxed": true,
    "filesystem": { "allowWrite": ["~/Library/Developer", "~/Library/Caches"] },
    "network": { "allowedDomains": ["github.com", "api.github.com", "swiftpackageindex.com"] }
  }
}
    
      
    This exact snippet is checked with claude doctor in CI. See the sandboxing docs for every option.

    Network modes
    
      
    Choose per run with --net. The mode only affects that container.
    
      
    
        
    ModeReachableUse it for
    
        
    --net full (default)EverythingNormal development, installs, dev servers with -p
    
        
    --net restrictedOnly Claude's own services, through an allowlist proxyRepositories you don't fully trust; stopping data from leaving
    
        
    --net restricted --allow devClaude, plus GitHub, npm, PyPI, crates.io, Go modules, DebianAllowlisted, but git clone, SwiftPM, pip and npm still work
    
        
    --net noneNothingOffline builds and tests with --shell; Claude itself can't run without its API
    
      
    
      
    In allowlist mode the container sits on an internal network with no route out. Its only exit is a small proxy that refuses every host not on the list, so tools that ignore proxy settings simply fail instead of leaking.
    
      
    In allowlist mode Seatbelt blocks every outgoing connection except one: a tinyproxy the launcher starts on a random local port for that session. The proxy refuses every host not on the list, so tools that ignore proxy settings simply fail instead of leaking. The proxy stops when the session ends; its log path is printed at start. --net none blocks outgoing connections entirely, while local services such as name lookup keep working.
    
      
    Allow another host
    
      
    Write one regular expression per line and pass the file. Lists are combined, and no rebuild is needed.
    
      
    printf '%s\n' '^api\.mycompany\.com$' '^(.*\.)?sentry\.io$' > ~/allow-myapp.txt
claude-sandbox --net restricted --allow dev --allow ~/allow-myapp.txt
# on macOS: claude-mac-sandbox --net restricted --allow dev --allow ~/allow-myapp.txt
    
      
    To see what was blocked, follow the proxy log; the launcher prints where it is when it starts.
    
      
    grep refused ~/.local/state/claude-mac-sandbox/proxy-*.log
    
      
    podman logs -f claude-proxy-<id> | grep refused
claude-sandbox --stop-proxies          # remove idle proxies
    
      
    Port publishing needs --net full. With the allowlist on, run the dev server from a separate --net full --shell session if you need to open it in your browser.
    
    
    

    
    
    
      
    Verify it works
    
      
    The kit includes an end-to-end test suite. Run it on your machine after setup, and after Podman or OS upgrades:
    
      
    cd ~/harness-container && tests/run-tests.sh
    
      
    cd ~/harness-container && tests/macos/run-tests.sh
    
      
    It uses throwaway folders, a throwaway Claude config and test-only Keychain items, so it doesn't touch your real login. It checks that writes outside the project are blocked (including through symlinks and child processes, and to ~/.zshrc, LaunchAgents and the Claude binary); that credential files, the ssh-agent and, when blocked, the Keychain are out of reach; that tokens in your environment aren't passed in; sign-in wiring; all three network modes, including attempts to skip the proxy; swift build, swift test and xcodebuild test of a sample Mac project; SwiftPM fetching through the allowlist; and per-project conversation storage. GitHub Actions runs it on macOS 14 and 15 for every push and weekly.
    
      
    It checks the host prerequisites; the image contents; that files written inside show up on your computer owned by you (new files, edits, renames, git commits, live while running); per-project conversation storage; that state survives exits, image rebuilds and a volume backup and restore; the security limits; all three network modes, including attempts to get around the proxy; and that each sign-in method is wired correctly.
    
      
    The same suite runs in GitHub Actions on x86_64 and arm64 for every push and weekly.  To also run real Claude conversations there, including resuming a conversation in a fresh container, add the repository secret ANTHROPIC_API_KEY or CLAUDE_CODE_OAUTH_TOKEN.
    
    
    

    
    
    
      
    Troubleshooting
    
      
    --continue finds no conversation, or the wrong one
        
    Conversations belong to the folder you started from. cd into exactly the same folder (same absolute path) and run it again. If you moved the project, use claude-sandbox --resume and press Ctrl+A, or resume by session ID. Conversations older than the retention period (30 days unless you changed it) are deleted.
    
      
    unknown option keep-id:uid or "invalid userns mode"
        
    Podman is older than 4.3. Upgrade it (Ubuntu 24.04+, Debian 12+, Fedora 38+).
    
      
    Allowlist mode can't find claude-proxy-…
        
    Podman is using the old CNI network backend. Install netavark and aardvark-dns, then run podman system reset. That deletes all containers, images and volumes, so export the volumes first (see "New computer" under Resuming work).
    
      
    Login page never returns to the terminal
        
    Expected inside a container. After signing in, the browser shows a code: paste it at Paste code here if prompted.
    
      
    Requests fail with 403 in allowlist mode
        
    The host isn't on the allowlist. Check the proxy log for the blocked name, then add it with an --allow file, or use --allow dev for package registries.
    
      
    "Permission denied" on project files
        
    Make sure you never ran the launcher or Podman with sudo: files created by a rootful run are owned by root. Fix ownership with sudo chown -R "$USER": . On Fedora or RHEL, keep the launcher's :Z labels; don't mount the same folder into other containers with :z.
    
      
    "refusing to mount" or "collides with a container system path"
        
    The launcher won't mount your whole home folder or /, or a folder whose path would shadow system directories inside the container. Move into a project folder, or pass --mount-at /workspace/my-app.
    
      
    "the requested cgroup controller is not available"
        
    Your user isn't allowed to set limits. Either do the optional resource-limits step, or ignore it: the launcher detects this and starts without limits.
    
      
    A tool I installed last time is gone
        
    Tools installed with npm -g, pipx, go install or cargo install persist. Ones installed with apt don't (and need root anyway): add them to the image with EXTRA_APT and rebuild.
    
          
    sandbox_apply: Operation not permitted
        
    Something tried to start a second sandbox inside this one, which macOS refuses. Usual causes: running swift or xcodebuild through xcrun (call them directly so the launcher's wrappers apply), Claude's built-in /sandbox being enabled (turn it off while using the launcher), or starting the launcher from inside another sandboxed app's terminal.
    
      
    "Operation not permitted" when writing a file
        
    The path is outside what the sandbox allows. If the tool really needs it, add --allow-write PATH for that run. Check the rules with claude-mac-sandbox --print-profile.
    
      
    git init, git config, git push -u or installing hooks fails
        
    .git/config and .git/hooks are read-only by default, because a changed git setting or hook would run code the next time you use git outside the sandbox. Run that step in a normal terminal, or pass --allow-git-config for one run and review the result.
    
      
    Claude says it isn't logged in, with the Keychain blocked
        
    The subscription login lives in the Keychain. With --no-keychain, sign in with --auth token or --auth apikey, which the launcher reads before the sandbox starts.
    
      
    Code signing fails in xcodebuild
        
    Signing with your certificates needs the Keychain: don't use --no-keychain for that run. Signing isn't covered by the automated tests yet.
    
      
    macOS asks whether Terminal may access Documents or Desktop
        
    That's macOS privacy protection, not the sandbox. Allow it for your terminal app, or keep projects in a folder such as ~/code.
    
      
    --net restricted needs tinyproxy
        
    Install it with brew install tinyproxy, or use full or no network.
